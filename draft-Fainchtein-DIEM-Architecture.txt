1.  Introduction

   This document presents a DNS and DNSSEC forward architecture.  That
   is, it assumes DNSSEC is required and defines an architecture in
   which different components or building blocks can be combined to
   achieve the needs of a particular use case, but where all of them are
   primarily realized using DNS and employ DNSSEC signing and
   validation.  For each building block or set of blocks introduced we
   reference the set of requirements it meets and identify other blocks
   with which it would likely be used or implemented.  This is intended
   to enable the construction of Digital Emblems that accommodate
   various granularity and temporality requirements.  Note:Digital
   Emblem protocols that do not use/require DNSSEC signing and
   validation thereof should specify how they handle emblem validation
   (to the extent required for their intended use cases).  Among the
   variations discussed in this document are cases where

   *  All of the DE's key information provided within DNS ();

   *  DE uses DNS pointers to resources outside of DNS that contain the
      emblem's key information (Section 8);

   *  DE primarily consists of a single RR (Section 4);

   *  DE consists of a bundle of separated RR's (RRSet) where each RR
      contains one or more pieces of the DE's core information ();

   (Note:This list is not intended to be all inclusive.)

3.  Assumptions

   This document presents a DNS and DNSSEC forward architecture.  That
   is, it assumes DNSSEC is required and defines an architecture in
   which different components are primarily realized using DNS and
   DNSSEC. * Cryptographic validation of Digital Emblems is required and
   is performed using DNSSEC. * Given the use of DNSSEC, all cases must
   meet the assured response requirement and a baseline version of
   consistent content.  We discuss this in more detail and present a
   mechanism for supporting selective disclosure in Section 5.

   *  Single RR w/everything vs multi RR/RRSet with each RR containing

   *  Type(s) of RR(s) used within the Digital Emblem

   *  TXT vs no TXT

5.  Zone Cut Structure for Digital Emblems

   Since we assume the use of DNSSEC, or rather that all RRs/RRsets
   making up a digital emblem are DNSSEC signed, the authoritative
   server cannot deny the existence of any associated RRs/RRsets.  As
   such, the only way to selectively disclose information within a
   digital emblem is for the authoritative server to hold two versions
   of any RRs that contain sensitive information or pointers thereto.
   Specifically

   *  One that contains the sensitive information or pointers thereto
      (hidden RR).  The hidden RR should only be presented if mutual
      authentication succeeds, and the requestor identity's membership
      in the set of authorized identities can be verified.  Moreover,
      given the sensitivity of its contents, the hidden RR should be
      encrypted.

   *  One of the same type and for the same FQDN that only includes the
      basic and/or non-sensitive emblem information (default RR).  This
      version of the RR should be returned by the Authoratative server
      if mutual authentication is not used, or if the requester's
      identity and/or authorization to see the sensitive content cannot
      be verified.

   It is recommended that only RRtype(s) where the default RR does not
   indicate that sensitive details have been redacted or intentionally
   excluded from its contents be chosen.

11.  Architecture for Authorizing Entities

~~~ goat

~~~
{: #authStruct title="Basic Structure for Authorization by an External Entity"}

   Digital Emblems that require authorization from one or more entities
   outside of their zone should include an _Authorizers_ field
   indicating the full list of entities that have authorized the
   issuance and use of a Digital Emblem.  As illustrated in the figure
   above, each authorizer entry should contain the following fields.

   *  The Authorizer's common name (<AUTH_NAME>);

   *  The Authorizer's FQDN (<AUTH_FQDN>);And

   *  A collision resistant hash of all constraints the Authorizer has
      put on their authorization of the Digital Emblem, accompanied by a
      version number associated with the constraint set signed by the
      Authorizer (signed(HASH(constraints))).

   To enable this the Authorizer publishes a DNSSEC signed authorization
   RR/RRset at the subdomain <DE_Name>.authorized.<AUTH_FQDN>.  Within
   the RR/RRset they publish the version number of the current
   constraint set as well as the start and end date indicating the
   timeframe over which their authorization is valid.  The authorizer
   then computes the hash of their constraints and signs over this, the
   constraint version number and the start and end dates of their
   authorization.  To finalize the authorization, the authorizer sends
   the signed constraints hash and versioning metadata to the bearer,
   who then uses this to update the set of authorizers within the
   Digital Emblem.  Note:To ease transitions from one set of constraints
   to another, or to handle reissuance of the authorization upon its
   expiration, Authorizers may host multiple authorization RRs/RRsets
   for the same emblem.
